# 复盘与下一步

## 最难的工程问题

本次实现最复杂的是让模型有选择空间，同时防止建议时间被误认为用户授权。仅在提示词写“不要擅改”不够，因此保存工具自己读取可信输入，区分原要求、替代建议和精确确认；报告从数据库写入结果生成，模型文本不能宣告保存成功。

第二个问题是防重与冲突互相影响。草稿如果占位，重复请求会看到自己的占位；如果不占位，两个素材可能建议同一时段。实现选择排除自己的业务键，同时让所有其他草稿（包括待确认）参与冲突检查；唯一约束和事务覆盖并发保存。素材/规则/方案发生变化时拒绝静默覆盖。

## 本次迭代带来的认识

这些是代码实现中可核对的结论，不代替候选人的个人学习经历：

1. 工具成功、业务完成、等待确认是三个状态，必须分别表达。
2. 固定业务校验可以约束模型动作，但不能用确定性分支伪装真实模型决策。
3. 幂等不能只依赖进程内集合；跨进程重放和并发需要持久化约束。
4. Trace 必须从真实执行自动生成，并明确 Mock 与真实模式的证据边界。
5. 官方模型接口也会变化；名称应可配置，未验证的接入不能写成已成功调用。
