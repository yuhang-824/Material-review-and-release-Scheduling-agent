# 需求与成功标准

## 用户与业务问题

内容运营需要把一批素材从“待处理”转为可审核的排期草稿。素材信息、版权风险、既有排期可能阻止原计划执行。系统应告诉运营哪里需要补充或确认，避免把建议误认为已执行。

## 输入与结果

可信输入为 CLI JSON：请求编号、1–10 个素材 ID、频道、带时区的要求时间、是否硬性时间，以及运营明确确认过的 `confirmed_alternatives`。素材库、补查库、规则、既有排期来自合成 JSON。所有时间规范化到 UTC+08:00，精确到分钟。

每个素材输出审核状态、结构化风险、原时间、建议时间、待确认项、实际草稿保存状态、草稿编号和处理结果。始终返回 `published: false`。

## 范围与边界

- 只保存本地 SQLite 草稿，无发布接口、定时发布或真实内容平台接入。
- 一个草稿占一小时，采用半开区间 `[开始, 开始+1小时)` 判断重叠；相邻整点可衔接。
- 查询范围是首选时间起四个一小时时段、同一日、08:00 至 22:00 前；并非全局最优排期器。
- 改变用户给出的时间，无论是否硬性要求都标记待确认；硬性要求始终保留，不通过模型文字声称已满足。
- CLI 是本地可信运营边界，确认由用户编辑输入提供。它没有鉴权，不适合直接暴露为多人 HTTP 服务。
- 资料缺失先尝试补查；确定违规阻断；不确定版权转人工；上述情况均不保存可用排期草稿。

## 可执行成功标准

| 验收点 | 预期行为 | 证据场景 |
|---|---|---|
| 正常排期 | 审核通过，原时间可用，保存 ready 草稿 | normal |
| 信息缺失 | 补查失败后列出缺失字段，无草稿 | missing_metadata |
| 规则风险 | 版权和禁用词风险可追溯，阻断保存 | rule_risk |
| 时段冲突 | 18:00 已占，建议 19:00，草稿待确认 | slot_conflict |
| 重复提交 | 同一素材、频道、原时间只存在一份草稿 | duplicate_submission |
| 保存失败 | 明确 failed，草稿编号为空，数据库零新增 | save_failure |

额外验证更换占用时段后建议改变、补查成功、确认升级、人工风险、查询失败、读取失败、无时段、批量占位、步数上限和不可信素材文本。所有规则见评估文档与可执行测试。

## Agent 要求

真实模式必须经历模型工具选择、执行、返回观察、再次模型选择的循环；不能把离线策略当作真实 ReAct 证据。默认最多 32 次模型选择/工具调用，允许配置 1–200；上限耗尽返回 `incomplete`，即便部分草稿已保存也不宣称整单完成。
